- **File:** `frontend/src/utils/parental.js` : 21-49

### 5. [CRITICAL] Every vault-backed secret is a pydantic_settings field whose literal default is computed once from the vault at import time, but pydantic-settings' built-in env-var source still runs afterward and silently overwrites that default if an OS/Railway env var of the same name exists — so a same-named env var permanently wins over whatever is in the vault, with no error and no log line.
- **File:** `backend/app/config.py` : 97-146 (e.g. 97: jwt_secret, 102-103: google_client_id/apple_client_id, 106-108: webauthn_rp_id/webauthn_origin, 119: sync_api_key, 129: anthropic_api_key, 134-136: stripe_*, 141: tmdb_api_key, 146: sentry_dsn)

I reproduced this directly: with `JWT_SECRET` set in the process environment and a stub `_get_secret` returning a different 'vault' string, `Settings().jwt_secret` resolved to the *env var* value, not the vault value, every time. This matters here because the project's own deployment runbook (`.cursor/skills/adajoon-deployment/SKILL.md`, and the incident doc `.cursor/skills/adajoon-skill-improvement/learnings/2026-04-04-worker-jwt-secret-missing.md`) explicitly instructs setting `JWT_SECRET` (and other secrets) as a Railway env var on every service (`JWT_SECRET = ${{backend.JWT_SECRET}}`), and the CLAUDE.md skill notes the vault migration only recently 'superseded' the old plain-env-var description (2026-11-08) — i.e. these env vars are very likely still sitting on the Railway services alongside the vault.
- **Impact:** Admin rotates a leaked JWT secret (or Stripe secret key, sync API key, etc.) via Admin → Secrets, vault_admin_service.set_secret() writes the new value into the vault successfully, and get_secret_status() correctly reports source: 'vault'. But because the old env var of the same name is still configured on the Railway service (per the team's own documented deployment pattern), the running process's `settings.jwt_secret` keeps using the stale value forever — not just until the next restart, but even across restarts/redeploys, since the env var re-wins every time Settings() is constructed. The admin has no way to detect this: the UI shows 'Set in vault' and tells them a restart will apply it, but it never will as long as the env var exists. For jwt_secret specifically this means a 'rotated' secret never actually rotates, defeating the entire point of the compromise-response rotation flow.

## Coding Best Practices

### 1. [CRITICAL] AI search uses the synchronous anthropic.Anthropic client inside async def functions, blocking the whole event loop for the full LLM round-trip.
- **File:** `backend/app/services/ai_search_service.py` : 355-383, 450-474
- **Evidence:** In async def ai_search_channels (and the near-identical async def ai_search_radio), the code does `client = anthropic.Anthropic(api_key=settings.anthropic_api_key)` then calls `message = client.messages.create(model=..., max_tokens=1024, ...)` directly (no `await`, no `run_in_executor`/threadpool offload). This is the blocking (non-async) Anthropic SDK client, and `messages.create` is a synchronous network call to api.anthropic.com that can easily take 1-10+ seconds.
- **Impact:** This service is reached from the unauthenticated, public endpoint POST /api/search/ai (backend/app/routers/ai_search.py) with only a short min_length/pattern check -- no auth, no rate limit visible in the router. Every uncached AI search call pins the single asyncio event-loop thread for the entire duration of the synchronous Anthropic API call, during which FastAPI cannot service any other concurrent request (channel browsing, radio streaming endpoints, auth, health checks, etc.) on that worker. A handful of concurrent AI-search requests (or a trivial scripted flood of them, since the endpoint takes free-text and isn't gated beyond ai_search_enabled) can stall the entire backend process for all users for seconds at a time.

### 2. [CRITICAL] The Stripe webhook handler, which mutates billing state for real users, has zero test coverage anywhere in backend/tests/.
- **File:** `backend/app/routers/subscriptions.py` : 227-318
- **Evidence:** stripe_webhook() verifies signatures, then branches on checkout.session.completed / customer.subscription.updated / customer.subscription.deleted to set user.subscription_tier, user.subscription_status and user.subscription_ends_at (lines 261-316). A grep of backend/tests/ for 'subscription' and 'stripe' returns no matches at all, and backend/tests/ has no test_subscriptions.py file. There is no test for: a valid signature with a missing/malformed metadata.user_id (data["metadata"]["user_id"] at line 263 would KeyError/ValueError with no try/except around it), an unknown stripe_customer_id, or the canceled/unpaid/past_due downgrade-to-free branch (lines 288-290).

### 3. [HIGH] The Stripe webhook handler has no try/except around event processing, so a realistic webhook payload missing expected fields raises an unhandled KeyError and returns a raw 500 instead of a handled error.
- **File:** `backend/app/routers/subscriptions.py` : 261-316
- **Evidence:** `user_id = int(data["metadata"]["user_id"])` and `tier = data["metadata"]["tier"]` (line ~263-264) assume `metadata` always contains both keys. A `checkout.session.completed` event without that metadata (e.g. a test event sent from the Stripe dashboard, or any checkout session not created through `create_checkout_session`) raises `KeyError`, which nothing in this function catches - unlike the signature/payload parsing above it, which is wrapped in `try/except ValueError` / `except stripe.error.SignatureVerificationError`.
- **Impact:** Stripe will see the 500 as a failed delivery and retry the webhook repeatedly (and alert on repeated failures); real subscription-activation events that happen to omit/alter metadata are silently dropped as unhandled server errors instead of being logged and acknowledged, which is inconsistent with every other exception path in this same file.

### 4. [HIGH] AddItemRequest.item_data is typed as a plain `str` with no Pydantic validation that it is actually valid JSON, and the value is stored verbatim; GET /api/playlists/{id} later calls json.loads() on it with no exception handling, so any malformed item_data submitted via POST permanently crashes playlist retrieval with an unhandled 500.
- **File:** `backend/app/routers/playlists.py` : 36-39, 210-245, 144
- **Evidence:** playlists.py:36-39: `class AddItemRequest(BaseModel): item_type: Literal["tv","radio"]; item_id: str; item_data: str  # JSON string with name, logo, etc.` — no validator checks it parses as JSON. playlists.py:236-245 `add_playlist_item` stores `item_data=request.item_data` as-is. playlists.py:144 `get_playlist` then does `"item_data": json.loads(item.item_data or "{}")` with no try/except around it (unlike every other DB-touching handler in this file, which wraps mutations in try/except). Contrast with auth.py's FavoriteRequest, which types the equivalent field as `item_data: dict = {}` (Pydantic-validated) rather than a raw string, showing this is a real oversight not an intentional design choice.
- **Impact:** Any authenticated user can POST /api/playlists/{id}/items with item_data="not json" (or any non-JSON string, e.g. empty string handled, but garbage text is not). The item is accepted and stored since the Pydantic model only requires `str`. Every subsequent GET /api/playlists/{id} call for that playlist then raises an uncaught json.JSONDecodeError inside the route, returning an unhandled 500 and breaking the playlist-view endpoint. Because playlists can be marked is_public=True, a single malicious or buggy client call poisons the playlist for every other user who later views it via GET, not just the submitter — this is a real, trivially reproducible DoS of a core feature caused purely by missing input validation on the body field.

### 5. [HIGH] Admin secrets-tab operations call the synchronous VaultClient (blocking httpx.get/post) directly from async route handlers with no offload to a thread.
- **File:** `backend/app/services/vault_admin_service.py` : 117-154
- **Evidence:** get_secret_status()/set_secret()/delete_secret() are plain `def` functions calling `vault.has()`, `vault.set()`, `vault.delete()` from app/vault_client.py, whose methods (`_ensure_token`, `get`, `set`, `delete`, `has`, `_is_sealed`) use the blocking module-level `httpx.get(...)`/`httpx.post(...)` (not httpx.AsyncClient) with a default timeout of 10s. These are called with no `await` and no `run_in_executor`/`run_in_threadpool` directly from `async def admin_list_secrets`, `async def admin_set_secret`, `async def admin_clear_secret` in backend/app/routers/admin_secrets.py:33-77.
- **Impact:** Each admin Secrets-tab action (list, set, or clear a secret) can issue up to 3 sequential blocking HTTP round-trips to the Vault service (token fetch, health check fallback, and the get/set/delete call itself), each with up to a 10s timeout. Because these run inline on FastAPI's async event loop with no threadpool offload, a slow/unreachable Vault instance stalls the entire process -- blocking every other concurrent user request (channel/radio/movie browsing, auth) for the full duration, not just the admin's own request.

### 1. [CRITICAL] SlowAPIMiddleware is never registered, so the limiter's default_limits=["100/minute"] from limiter.py never actually applies to any route — only the small set of endpoints carrying an explicit @limiter.limit(...) decorator get rate-limited at all.

### 17. [MEDIUM] python-jose is pinned to 3.3.0, which has two publicly known CVEs (CVE-2024-33663 and CVE-2024-33664) that are only fixed in 3.4.0, and this exact library is used for all session/auth JWTs.
- **File:** `backend/requirements.txt` : 11
- **Evidence:** requirements.txt:11 pins `python-jose[cryptography]==3.3.0`. CVE-2024-33663 is an algorithm-confusion vulnerability (crafted JWKs with certain EC/OpenSSH-format keys can bypass signature verification) and CVE-2024-33664 is a JWE decompression-bomb DoS; both were only patched in python-jose 3.4.0 (released after 3.3.0). This is not a dead dependency: `backend/app/routers/auth.py` imports `from jose import JWTError, jwt` and uses `jwt.encode`/`jwt.decode` to mint and verify the app's session tokens, challenge tokens, and (at auth.py:374/380) Apple identity tokens.
- **Impact:** The direct exploit path for CVE-2024-33663 requires JWK-based/asymmetric key verification, and this codebase's own usage restricts decoding to `algorithms=[settings.jwt_algorithm]` with `jwt_algorithm = "HS256"` (config.py:98), which narrows (but does not eliminate the library-level) exposure, so it is not immediately exploitable by an anonymous user against the main session-token flow as currently configured. However, pinning to a version with two documented CVEs in the library that mints/verifies every user's auth token is a real supply-chain/version-currency gap: any future change that adds asymmetric-key JWT handling (e.g. the Apple identity-token verification path at auth.py:374-380, which parses external-issued tokens) would inherit the vulnerable code paths with no code change required, and a fixed release (3.4.0) is already available to pick up instead. Exploitability today is low/edge-case; the finding is that a known-CVE version is intentionally locked in a security-critical dependency with no compensating comment/justification.
