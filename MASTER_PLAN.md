### Recent incidents (all resolved same-day)
Recurring lesson across three of these: **CI green doesn't prove the real deploy artifact builds** — it only proves *a* build succeeded under CI's toolchain, which has repeatedly differed from Railway's. Validate the actual Railway build/deploy after merging anything touching Dockerfiles or lockfiles, don't trust CI alone.
- **2026-11-09** — prod domains were bound to the backend service instead of frontend (visitors got raw JSON). Moved both custom domains to frontend.
- **2026-11-08** — prod DB was stuck behind the committed Alembic chain (`start.sh` never ran migrations). Fixed: `alembic upgrade head` now runs on every boot.
- **2026-11-23** — `python:3.15-slim` bump (dependabot #99) broke the real Docker build (no `pydantic-core` wheel for CPython 3.15, source compile fails in the slim image). CI's Docker-build job only ran on push to `main`, not on PRs, so this wasn't caught pre-merge. Reverted to `3.12-slim`. **Fixed the gap too (2026-11-24):** added `build-images-pr` to `ci.yml` — a build-only (no push), no-registry-login job that runs on every PR, so a Dockerfile/lockfile change that breaks the real build now fails CI directly instead of only surfacing after merge.
- **2026-11-23** — `maplibre-gl` v5→v6 bump (dependabot #130, fixes a critical XSS advisory GHSA-jrc7-96c5-q579) needed two real code fixes to actually ship: a namespace import (v6 dropped the default export) and explicit Worker URL registration via `?worker&url` (v6's `import.meta.url`-based worker resolution doesn't survive Vite's hashed prod bundling — production-build-only bug, `npm run dev` never shows it).
- **2026-11-23** — the above fix's locally-regenerated lockfile (made with npm 10.9.9 + `--legacy-peer-deps`) was missing platform-specific optional-dependency entries, so it passed GitHub Actions' `npm ci` but failed Railway's (npm 11.x, stricter). Fixed by regenerating with npm 11.20.0 to match Railway's build image. Site was never actually down — Railway doesn't cut over to a failed build.
- **2026-11-23 → 2026-11-27, fixed for real on the last occurrence** — `/api/*` saw 502/504s after a deploy, worked around each time by restarting backend then frontend. That workaround masked the actual bug for days: `frontend/nginx.conf.template`'s `proxy_pass` used a literal `backend.railway.internal` hostname, which nginx resolves via DNS **once**, at config-load time, and never again for the life of the process. Railway redeploys the whole project together on any push, so the backend container gets a new internal IP on every deploy — this nginx process had no way to find out, so every `/api/*` request hit a dead IP until something forced a fresh nginx process (a restart). On 2026-11-27 this recurred and stayed broken for roughly an hour (67-69% error rate) before being properly root-caused. **Fixed:** `start.sh` now reads the container's real DNS resolver from `/etc/resolv.conf` at boot, and `nginx.conf.template` adds `resolver ${DNS_RESOLVER} valid=10s;` with the backend target moved into an nginx variable, forcing a fresh DNS lookup on each new upstream connection instead of caching forever. Verified behaviorally (not just `nginx -t`): built the real `start.sh`+template pipeline against a live nginx with a throwaway test DNS server and two dummy backends, confirmed the original config has no recovery path without a restart, and confirmed the fix self-heals within the resolver's TTL after simulating a redeploy, with zero restarts. That same test caught a second real bug before it shipped: a variable-based `proxy_pass` disables nginx's usual location-prefix rewrite, so `/api/ping` was reaching the backend as a bare `/api/` — fixed via `$request_uri`. Also deleted `frontend/nginx.conf`, a dead file the Dockerfile never referenced.

## Known tech debt / explicitly deferred
*Validated against the actual code/GitHub state on 2026-11-24 — removed two items that turned out to already be resolved/stale (see below), corrected one whose root cause was described wrong, and corrected the stale-branch count.*
- Sentry has no DSN set — inert until configured (Admin → Secrets, or `SENTRY_DSN`/`VITE_SENTRY_DSN`).
- No PR merged in this session had a true GitHub-enforced approval (single identity can't self-approve; confirmed via the GitHub API — `main` has no branch protection rule at all). Consider branch protection if a harder gate is wanted.
- Feature-gating is a no-op beyond ads — confirmed no 4K-quality or offline-download tier check exists anywhere in `backend/app/routers/`. Advertised Pro/Family features, real monetization gap.
- No audit-log tamper-evidence — confirmed `AdminAuditLog` (`backend/app/models.py`) and `audit_service.py` have no hash chain or write protection. No staging environment either — both deliberate for team size, revisit if it grows.
- **Vault secret "rotation" can silently no-op, but not for the reason previously written here** — corrected after reading `config.py`/`vault_admin_service.py`: `_get_secret()` actually tries Vault *before* any env var fallback, so that's not the bug. The real issue: `Settings()` (and so every secret it reads via `_get_secret`) is instantiated **once** at process startup and never re-read. The admin Secrets UI's `set_secret()` writes a new value straight to Vault and returns success — correctly — but the *already-running* backend process keeps using whatever it cached at boot until something restarts it, with no warning to the admin that a restart is required. A "rotated" leaked JWT secret or API key is therefore still live in the running process until a manual/deploy restart happens. Still open; the real fix needs either a restart-trigger on write or moving rotatable secrets off cached `Settings` fields to a live per-call lookup (with its own caching/TTL) — not a quick patch, hasn't been attempted yet.
- ~~"Build Docker Images" CI job never runs on pull requests~~ — **fixed 2026-11-24**, see incident note above.
- ~~No uptime/reachability monitoring~~ — **stale, already false.** Railway's own traffic logs show both UptimeRobot and a custom `RevestAlive/0.1` bot actively polling `/` and several routes every ~60s. Monitoring exists; whatever alerting is wired to it wasn't visible from this session, so if alerts aren't actually reaching anyone that's a narrower, different gap than "nothing watches the site."
- **~110 stale branches** (not "38+" as previously stated — recounted via the GitHub API) — merged `claude/*`/dependabot/`railway/*` branches that never auto-deleted. This session's git access still can't delete refs (`git push --delete` gets HTTP 403 from the sandbox proxy, and none of the available GitHub tools expose branch/ref deletion). Needs cleanup via GitHub's UI directly, or enabling "Automatically delete head branches" in repo settings so this stops recurring.
